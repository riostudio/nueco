# Nueco — Business Logic Map

Generated by scanning `backend/` (FastAPI + MongoDB, deployed on Railway) and `frontend/`
(Expo/React Native, expo-router) for calculations, state transitions, validation rules, and
domain workflows. UI layout, styling (`theme.ts`, `components/*.tsx`), and pure database
bootstrapping are intentionally excluded except where a "setup" file also encodes a real
business rule (e.g. index choices that enforce uniqueness invariants).

---

## 1. Architectural Overview

Nueco is two codebases sharing one domain: a FastAPI backend and an Expo/React Native
client, connected over a REST API. Business logic is not perfectly separated from
infrastructure in either — this section maps where it actually lives today.

### Backend (`backend/`)

- **Feature modules** (`auth/`, `canva/`, `dailybrew/`, `textai/`, `attachments/`, `notes/`,
  `events/`) each follow (to varying degrees) a `router.py` (HTTP parsing/shaping only) →
  `service.py` (business rules, framework-agnostic) → `schemas.py` (Pydantic DTOs, no
  `fastapi`/`motor` imports) split. `notes/` and `events/` are the newest and cleanest
  examples: their `service.py` files raise plain Python exceptions
  (`NoteNotFoundError`, `EventPayloadTooLargeError`, etc.) instead of `fastapi.HTTPException`,
  and take a `db` handle via constructor injection rather than importing a global.
- **`server.py` is the architectural exception.** It still owns the FastAPI app object,
  middleware, CORS, and DB index creation (legitimate infra) — but it *also* contains
  substantial, un-extracted business logic: the entire push-reminder delivery pipeline
  (`push_tick`/`push_receipts_tick`), AI feedback triage, GDPR account erasure, E2EE
  key-escrow blob validation, and feature-telemetry validation. None of this is behind a
  `service.py` seam. This is the single largest concentration of business logic outside a
  dedicated module in the whole backend.
- **Known compliance gaps** (documented in the repo's own `CLAUDE.md`): `attachments/service.py`
  and `textai/service.py` import `fastapi.HTTPException`/`UploadFile` directly, breaking the
  framework-agnostic rule for entities/use cases; `auth/service.py` and `canva/service.py`
  import `AsyncIOMotorDatabase` directly (accepted short-term debt).

### Frontend (`frontend/src/`)

- **Pure "Core" modules** contain the most genuinely framework-free logic in the repo — no
  `react`/`react-native`/`expo-*` imports, callable from plain Node, most with a matching
  `*.test.ts` file: `crypto/noteCryptoCore.ts`, `crypto/eventCryptoCore.ts`,
  `calendarSyncCore.ts`, `recurrence.ts`, `textContent.ts`, `share/normalizeShareIntent.ts`,
  `share/socialSource.ts`.
- **Impure orchestration wrappers** sit around those cores and add the device/network/storage
  concerns the core logic deliberately avoids: `crypto/noteCrypto.ts`/`eventCrypto.ts` (device
  keystore + feature flags), `offlineSync.ts` (file-based local store + sync queue),
  `calendarSync.ts`/`calendarSyncTask.ts` (AsyncStorage settings + OS background task),
  `deviceCalendarSync.ts`, `notifications.ts`, `dailyBrew/dailyBrew.ts`.
- **The client is local-first by design**: every create/update/delete writes to an on-device
  JSON file store and enqueues a durable sync-queue item *before* any network call happens.
  Reconciliation with the server is timestamp-based for notes and last-write-wins for events.
- **E2EE is a cross-cutting layer**, not a single module: `crypto/e2ee.ts` provides AES-256-GCM
  + PBKDF2 primitives and a password/recovery-code key-escrow scheme; every note/event
  crossing the wire is encrypted/decrypted at the `noteCrypto.ts`/`eventCrypto.ts` boundary,
  gated by build-time flags (`crypto/flags.ts`) so the feature can roll out in stages.
- **Screens (`app/*.tsx`) are presentation** and are excluded from this map except as callers —
  no screen was found to hide meaningful business logic that isn't already delegated to a
  hook or service file.

## 2. Core Domain Entities & Models

### User (backend `auth/models.py` doc + frontend `auth/types/auth.types.ts`)

| Field | Notes |
|---|---|
| `id`, `email` (lowercased), `name` | `name` may be E2EE ciphertext (see `enc_version`) |
| `password` | bcrypt hash, cost factor 12 |
| `email_verified`, `verification_token`, `verification_token_expiry` | 24h token TTL |
| `reset_token`, `reset_token_expiry` | 30min token TTL |
| `failed_login_attempts`, `locked_until` | lockout state machine (5 attempts → 30min lock) |
| `enc_version` | `1` = name is AES-256-GCM ciphertext; `null`/absent = legacy plaintext |
| `news_country`, `news_outlet_ids`, `custom_news_feeds`, `daily_brew_show_verse` | Daily Brew prefs |
| `canva_access_token`/`canva_refresh_token` (Fernet-encrypted), `canva_token_expires_at`, `canva_connected_at` | Canva OAuth state, stored on the user doc, not a separate collection |

### Device / Session (`auth/models.py`)
- `device`: id, user_id, device_name, platform, fcm_token, last_active_at, registered_at.
- `session`: id, user_id, device_id, `refresh_token` (**SHA-256 hash only**, never raw),
  expires_at, created_at. Access tokens are session-bound via a `sid` JWT claim — deleting the
  session row revokes the access token instantly even if the JWT itself hasn't expired.

### Note (`backend/notes/schemas.py` ↔ `frontend/src/types.ts`)
`id, title, content, tags: [{name, color}], is_pinned, linked_event_id (deprecated),
linked_event_ids: string[], images: string[] (base64), attachments: Attachment[],
has_attachments, user_id, enc_version, created_at, updated_at`.
- `enc_version = 1` → `title`/`content`/each `tag.name` are independent AES-256-GCM ciphertext
  tokens; `tag.color` and all other fields stay plaintext.

### Attachment (`backend/attachments/schemas.py` ↔ frontend `types.ts`)
`id, key (S3 object key, server-generated), url, filename, mime_type, size_bytes, uploaded_at`.

### CalendarEvent / Recurrence (`backend/events/schemas.py` ↔ frontend `types.ts`)
`id, title, description, location, start_time, end_time, linked_note_ids: string[],
reminder_minutes: 5|15|30|60|1440|null, device_calendar_event_id, user_id, enc_version,
created_at, recurrence: Recurrence|null, timezone (IANA name)`.
- Server-only scheduler fields (not in the client-facing schema but stored on the doc):
  `reminder_fire_at`, `reminder_status: pending|claimed|sent`, `reminder_claimed_at`.
- `Recurrence`: `freq: daily|weekly|monthly|yearly, byweekday: number[]|null (0=Sun..6=Sat,
  matches JS Date.getDay()), until: ISO date string|null (inclusive)`.
- `enc_version = 1` → `title`/`description`/`location` are ciphertext; `start_time`,
  `end_time`, `reminder_minutes`, `linked_note_ids`, `device_calendar_event_id` stay plaintext
  (needed for scheduling/matching without decryption).

### EscrowBundle (E2EE key escrow, `crypto/e2ee.ts` ↔ `backend/server.py`'s `WrappedKeyPut`)
`wrapped_by_password, wrapped_by_recovery (DEK wrapped by two independently-salted KEKs),
kdf_salt, recovery_salt, kdf: "pbkdf2", kdf_params, enc_version`. Entirely opaque to the
server — it stores blobs, salts, and KDF parameters, never the DEK or plaintext.

### SyncQueueItem (`offlineSync.ts`, on-device only)
`{ id, entity: 'note'|'event', operation: 'create'|'update'|'delete', payload, retries,
timestamp }` — persisted to `syncQueue.json`, never sent to the server as a document.

### Outlet / NewsItem (`backend/dailybrew/`)
- `Outlet` (catalog, static): `id, name, description, feed_url, topics: string[]`.
- `NewsItem` (fetched): `headline, link, source_name, published_at, logo_url`.

### PushToken / PushReceipt (`backend/server.py`, `db.push_tokens`/`db.push_receipts`)
- `push_tokens`: `user_id, token, platform, active, updated_at` — upserted on
  `(user_id, token)`, deactivated (not deleted) on unregister/`DeviceNotRegistered`.
- `push_receipts`: `ticket_id, event_id, token, created_at, checked` — tracks Expo delivery
  receipts pending resolution.

### FeatureEvent / Feedback (`backend/server.py`)
- `feature_events`: `id, user_id, event (≤64 chars), meta (≤2048 bytes JSON), ts` — metadata-only
  first-party analytics, deliberately capped to prevent note content leaking through.
- `feedback`: `id, user_id, sentiment (positive|negative), tag, text (≤2000 chars),
  aiCategory, aiPriority, aiSummary, appVersion, platform, noteCountAtSubmission, createdAt,
  status`.

### CanvaDesign (`backend/canva/schemas.py`)
`id, title (falls back to "Untitled design"), thumbnail_url, updated_at` — normalized shape
over Canva's own API response.

## 3. Critical Workflows & Pipelines

### 3.1 Signup → Verification → Login → E2EE Key Bootstrap
1. `POST /auth/signup` (rate-limited: 3/IP/hour) — rejects password mismatch or <8 chars;
   creates the user doc, sends a verification email (Resend API) with a 24h-TTL token link.
   If an unverified signup already exists and its token expired, the old account is deleted
   and signup is allowed to proceed fresh; if unexpired, blocks with "check your email."
2. `GET /auth/verify-email/{token}` — marks `email_verified=true`, unsets the token.
3. `POST /auth/login` (rate-limited: 5/email/min, 10/IP/min) — blocks unverified emails even
   with a correct password; checks `locked_until` before the password check; on failure
   increments `failed_login_attempts`, locking for 30min at ≥5; issues a session-bound
   access token (24h) + a 30-day refresh token (stored server-side only as a SHA-256 hash).
4. Client `AuthContext.login()`: sets user state immediately, fires
   `requestCalendarPermissionsAsync()` up front, then (if `E2EE_KEYS_ENABLED`)
   **awaits** `bootstrapKeyOnLogin(password)`:
   - No escrow exists yet → creates one, returns a **one-time recovery code** for the UI to
     force-display.
   - Escrow exists and password unwraps it → DEK stored in `expo-secure-store`.
   - Escrow exists but password fails to unwrap it (e.g. a password reset happened without a
     recovery-code re-wrap) → `needs_recovery`; the password is held in memory
     (`pendingPasswordRef`) to complete recovery later via `recoverKey()`.
5. In the background (not blocking UI): `fullSync({ force: true })` runs, then — only if key
   bootstrap didn't need recovery — the one-time, feature-flagged, **irreversible**
   plaintext→ciphertext migration (`migrateNotesToEncrypted`/`migrateEventsToEncrypted`) runs,
   then a fresh `/auth/me` fetch + `pushBackPlaintextName` reconciles the account name's
   `enc_version`.

### 3.2 Password Reset / Account Recovery (two independent paths)
- **Server-mediated reset** (forgot password): `POST /auth/forgot-password` (always returns
  success-shaped response — no email enumeration) → 30min-TTL emailed token →
  `POST /auth/reset-password` → **deletes every session for that user**, forcing re-login on
  every device. This does *not* know about the E2EE escrow, so the next login typically lands
  in the `needs_recovery` bootstrap state above.
- **Recovery-code re-wrap** (E2EE): `recoverKeyWithCode(code, newPassword)` unwraps the DEK
  using the recovery code, then `rewrapForNewPassword` generates a fresh password salt and
  re-wraps the *same* DEK — old ciphertext (all existing notes/events) stays readable; only
  the recovery salt is untouched.
- **Authenticated in-app password change**: `rewrapDekForNewPassword` — same DEK-preserving
  re-wrap, no recovery code needed since the current DEK is already unlocked in the session.

### 3.3 Note Create/Edit/Delete (local-first + E2EE + sync)
1. Editor calls `createNoteOffline`/`updateNoteOffline` → `encryptNoteForServer` (no-op if
   E2EE flag off or no DEK loaded) → write to local JSON store + in-memory cache → enqueue a
   `SyncQueueItem` → return immediately (UI never blocks on network).
2. If online, `processSyncQueue()` fires (or is deferred via `{ push: false }` during active
   autosave to avoid a temp-id swap racing in-flight edits).
3. On successful `create`, the local `local_${uuid}` temp id is swapped for the server-assigned
   id in storage.
4. On a queued `update`, before pushing, the current server note is fetched and its
   `updated_at` compared to the local one; **local wins only if strictly newer** — otherwise
   the local edit is discarded and overwritten by the (decrypted) server copy.
5. Failed queue items retry up to 5 times, then are dropped silently (no dead-letter).
6. `fullSync()` (throttled to once/20s unless forced) merges: server is authoritative for
   already-synced notes; still-`_isLocal` (never pushed) or `_pendingDelete` notes are
   preserved/dropped locally rather than overwritten.

### 3.4 Calendar Event Create/Edit/Delete (+ reminder scheduling)
1. Same local-first write/enqueue pattern as notes, but **no `updated_at` field exists on
   events** — conflict resolution is unconditional last-write-wins, not timestamp-compared.
2. On create/update, if `start_time`/`reminder_minutes`/`recurrence` changed, the backend
   recomputes `reminder_fire_at = start_time - reminder_minutes`; if that moment is already in
   the past, `reminder_status` is immediately set to `sent` so a backfilled/late-edited event
   never queues a stale reminder.
3. `createEventOffline` bypasses the generic queue processor and does an inline
   create-and-resolve, because callers (e.g. "link this new event to this note") need the real
   server id synchronously.
4. Device's local OS-notification id (`local_notification_id`) is a device-only field, never
   sent to/from the server — `fullSync`'s merge step explicitly re-attaches it to the
   server-refreshed event or the OS notification would be silently orphaned.

### 3.5 Reminder Push Delivery Pipeline (`push_tick`, cron ~1/min)
1. **Stuck-claim recovery**: any event stuck `claimed` for >5min (crashed prior tick) resets
   to `pending`.
2. **Atomic claim loop**: `find_one_and_update` repeatedly claims `pending` events with
   `reminder_fire_at <= now`, up to 500/tick — the atomicity is what prevents two overlapping
   ticks from double-sending.
3. **Message build**: up to 20 active push tokens per event; if E2EE (`enc_version` set),
   title falls back to generic "Event Reminder" rather than showing ciphertext.
4. **Batch send** to Expo (≤100/call); per-item `DeviceNotRegistered` errors deactivate that
   token; a whole-batch failure leaves those events `claimed` for the stuck-claim recovery to
   retry next tick.
5. **Recurrence rollforward**: only over the tick's own in-memory claimed list (never a fresh
   query — prevents a double-advance race); computes the next occurrence via
   `next_occurrence_on_or_after` (dateutil.rrule + zoneinfo, timezone-correct across DST) and
   resets the event to `pending` with a new fire time, or leaves it terminal `sent` if the
   series (`until`) has ended.
6. Separately, `push_receipts_tick` (cron ~every 15–20min) resolves Expo delivery receipts
   15min–24h after send, deactivating tokens Expo reports as unregistered — the main path by
   which stale tokens get pruned after an uninstall/reinstall.

### 3.6 Device Calendar Two-Way Sync
1. `calendarSyncCore.ts` (pure): given the current device-calendar read and prior per-event
   content hashes, decides create/update/delete actions. Deletion is only trusted when the
   selected-calendar set is unchanged since last run **and** this run's fetch was non-empty
   (guards against a transient empty read looking like a mass-delete).
2. `calendarSync.ts` (impure wrapper): throttles to once/15min (bypassable with `force`), uses
   an AsyncStorage-backed cross-process lock (2min TTL — needed because iOS can invoke the
   background task in a separate headless JS context where an in-memory flag is invisible),
   fetches device events for a −7d..+180d window, and persists per-device-event content hashes.
3. `calendarSyncTask.ts` registers this as an OS background task
   (`expo-task-manager`/`expo-background-task`, 15min minimum interval, both OSes treat that
   as a floor not a guarantee).
4. `deviceCalendarSync.ts` separately nudges Android's account-sync adapter after a write
   (`bumpDeviceCalendarSync`) and, on every app foreground, rewrites the device-calendar entry
   for any recurring Nueco event to its next upcoming occurrence
   (`refreshRecurringDeviceCalendarEntries`).
5. Known limitation: the server caps `GET /events` at 100 results, so a user with >100 real
   events can see an already-imported device event look "new" and get re-created.

### 3.7 Share-Intent → Note Draft
1. OS share sheet delivers a URL/text/files to `normalizeShareIntent.ts` (pure).
2. If the shared content resolves to a URL with a detectable brand (`socialSource.ts`:
   Instagram, TikTok, YouTube, Reddit, X, etc., or a generic "link" fallback for any other
   parseable host), it becomes a `sourcePost` card, not raw text — tagged `link` — and
   `unfurl.ts` best-effort fetches a title/thumbnail (TikTok oEmbed, Reddit's public `.json`
   API, or Open Graph scraping for the rest; **no SSRF guard** on the fetched URL, unlike the
   backend's custom-feed fetcher).
3. Shared images ≤5MB each (≤5MB cumulative per share) are inlined as base64; anything larger
   or non-image is queued as a `pendingFile` for the editor to upload via presigned URL with
   progress.
4. The resulting `NoteDraft` is handed to the editor through a one-shot module singleton
   (`pendingShareDraft.ts`) since route params can't carry base64 image data.

### 3.8 Voice Transcription → Note Text
`POST /textai/transcribe-base64` → backend normalizes the extension (`.caf`→`.m4a` for iOS's
raw recorder format), writes to a temp file, calls OpenAI Whisper (`whisper-1`) with **no
language hint** (deliberately — OS locale isn't a reliable proxy for spoken language) →
returns transcript text, guaranteed temp-file cleanup via `finally`.

### 3.9 AI Text Processing (`organize` / `summarize` / `smart_format`)
All three call `gpt-4o-mini` at `temperature=0.2`. `smart_format` forces JSON-mode output
classifying the note into `recipe|checklist|meeting_notes|general` and restructures into
type-specific HTML (recipe → Ingredients/Steps; checklist → `☐`-prefixed list; meeting_notes →
only the subset of Attendees/Discussion/Decisions/Action Items that have real content);
an unrecognized classification silently falls back to `general` rather than erroring.

### 3.10 Canva Connect → Design Export
1. `build_authorize_url`: PKCE `code_verifier` (128 chars) + SHA-256 `code_challenge`, 32-byte
   `state` stashed in an **in-memory** dict (10min TTL) — documented as breaking under
   horizontal Railway scaling, single-replica assumption.
2. `exchange_code`: single-use state pop, HTTP Basic OAuth token exchange, tokens Fernet-encrypted
   before storage on the user doc.
3. Every API call refreshes first if the token expires within 60s; Canva refresh tokens are
   **single-use**, so the new one must be persisted immediately or the next refresh breaks —
   on refresh failure the connection is torn down (`disconnect()`) rather than retried forever.
4. `create_export`/`get_export_status`: requests a PNG export job, polls status, returns the
   first URL in Canva's `urls` array.

### 3.11 Daily Brew Card Assembly (news + weather + events + verse)
1. **Headline selection** (`get_headlines_for_user`): resolves followed outlet ids against the
   full catalog+custom feeds, re-sorted into the user's follow order, truncated to the first 3
   outlets; fetches all concurrently; distributes a `limit` (default 3) of headline slots by
   outlet count (1 outlet → all slots; 2 → ceil/floor split; ≥3 → 1 each + round-robin
   remainder), then backfills from a pooled freshness-sorted leftover list if any outlet came
   up short.
2. Server-side per-outlet cache (15min TTL, double-checked-locked, 10min background prewarm
   loop) means user-facing requests rarely pay cold RSS-fetch latency; a dead feed falls back
   to last-known-good rather than erroring.
3. Client-side: `fetchWeather()` tries a ≤15min-old cached GPS fix first, races a fresh fix
   against an 8s timeout, calls Open-Meteo, and maps WMO weather codes to one of 6 condition
   buckets. `getVerseForDate()` deterministically rotates through a 70-verse array by
   day-of-year modulo. All three (events/weather/news) merge into one cache object
   independently so one slow fetch doesn't block the others from showing.

### 3.12 Account Deletion (GDPR Art. 17 Erasure)
1. Re-verifies the account password fresh from DB (defense against a stale/forged session).
2. Deletes all S3 attachments first (`asyncio.to_thread`, since it's sync boto3 and would
   otherwise block the event loop for the whole paginated walk).
3. Deletes every `user_id`-scoped document across `notes, events, push_tokens, push_receipts,
   feature_events, devices, sessions` (each in its own try/except so one failing collection
   doesn't abort the rest), then the `users` doc itself. Irreversible, no soft-delete.

### 3.13 Data Export (GDPR Art. 20 Portability)
Reads from the **local decrypted** note/event cache (not the server, which only ever holds
ciphertext), excludes `_pendingDelete` records, and writes a JSON file
(`{app, format_version, exported_at, profile, notes, events}`) shared via the OS share sheet.
Notably exports only the deprecated singular `linked_event_id` (not the plural array), and
omits images/attachments/location/recurrence/timezone fields entirely.

### 3.14 Feedback Submission + Milestone Toast
- Toast eligibility (`feedbackToast.ts`): first shown after a user's 5th note ever created
  (lifetime counter); a dismiss-without-answering schedules exactly one retry at
  `count + 5`; a second dismiss gives up permanently; answering (thumbs up/down) also
  permanently resolves it.
- Submission (`POST /feedback`, rate-limited 5/user/24h): non-empty free text is triaged by
  `gpt-4o-mini` into category/priority/summary (JSON-mode); **triage failure never blocks the
  save** — the feedback record is always persisted, with AI fields left `null` on failure.

## 4. Validation & Invariant Rules

### Authentication & Sessions
- Password: minimum 8 characters, must match confirmation — enforced in the router, not schemas.
- Login lockout: 5 failed attempts → 30-minute lock (`locked_until`).
- Login rate limits: 5/email/min, 10/IP/min. Signup: 3/IP/hour. Password reset: 3/email/hour,
  5/IP/hour.
- Access tokens are JWT (HS256) but **session-bound** — a deleted session row invalidates the
  token immediately regardless of JWT `exp`.
- Refresh tokens: 64-byte random, stored server-side only as a SHA-256 hash; a password reset
  deletes every session for the user (forces global re-login).
- Verification tokens: 24h TTL, single-use (`$unset` on use). Reset tokens: 30min TTL, single-use.
- `forgot-password`/`resend-verification` always return success-shaped responses regardless of
  whether the email exists (email-enumeration prevention).

### Payload Size Caps
- Note title ≤5,000 chars, content ≤1,310,720 chars (256KB × 5 headroom), images ≤8MB total —
  all ×5 "ciphertext headroom" over the intended plaintext limit to tolerate AES-GCM+base64
  inflation without falsely rejecting encrypted notes.
- Event title ≤1,000 chars, description ≤25,000 chars, location ≤1,500 chars (same 5×
  headroom rationale, duplicated independently in `events/service.py`).
- E2EE wrapped-key blobs (`wrapped_by_password`, `wrapped_by_recovery`, `kdf_salt`,
  `recovery_salt`) ≤8,192 chars each.
- Feature-telemetry event name ≤64 chars, metadata JSON ≤2,048 bytes (explicit guard against
  smuggling note content through the analytics channel).
- Feedback text ≤2,000 chars.
- Attachments: 1 byte–100MB, extension **and** MIME type both must be on an explicit whitelist
  (image/video/audio/PDF/Office formats); object key is always server-generated
  (`note-attachments/{user_id}/{uuid}.{ext}`), never client-supplied — prevents writing outside
  the caller's own namespace. Download/delete both re-check the key is prefixed with the
  caller's own `user_id`.

### E2EE Invariants
- `enc_version == null`/absent = legacy plaintext, always passed through unmodified;
  `enc_version == 1` = AES-256-GCM ciphertext. Never a third state.
- Encrypting an already-`enc_version == 1` note/event is a strict no-op (never double-wraps).
- A field-less patch (e.g. `is_pinned`-only) never stamps `enc_version` — respects the
  backend's `exclude_unset` PATCH semantics; stamping it would falsely claim encryption for
  fields that were never touched.
- Per-field decrypt failure (wrong key/tamper/corruption) substitutes a placeholder
  (`⚠️ Unable to decrypt`) rather than throwing — one bad field/note can't blank a whole list.
- The escrow bundle never contains the raw DEK in any serialized form (property-tested).
- The DEK persists **only** in the OS-native secure keystore (`expo-secure-store`); on web,
  storage is a no-op and E2EE is effectively inert (notes/events stay plaintext).
- Password change/reset always preserves the same DEK (re-wrap, not re-generate) — existing
  ciphertext must remain readable across a credential change.
- The one-time legacy→encrypted migration is independently gated per note/event dataset, is
  explicitly documented as irreversible, and only marks itself "done" if the entire pass
  completed with zero per-item failures — otherwise it silently retries on next login.

### Sync Invariants (`offlineSync.ts`)
- Every write lands locally + is queued **before** any network call (true local-first).
- A queued `delete` over an unsynced `create` cancels both (never reaches the server); a
  `delete` always wins over any other pending op for the same id.
- A note's local edit only overwrites the server if its `updated_at` is *strictly* newer;
  otherwise the local edit is discarded. Events have no such check — always last-write-wins.
- Failed sync-queue items retry up to 5 times, then are dropped (no dead-letter queue).
- A device event's disappearance is only trusted as a real deletion when the selected
  device-calendar set is unchanged since the last run and the current fetch was non-empty.

### Reminder / Recurrence Invariants
- `reminder_fire_at` in the past at compute time → immediately marked `sent`, never queued.
- The atomic `find_one_and_update` claim step guarantees no two overlapping tick invocations
  ever claim the same event — the structural guarantee that prevents double-sends.
- Recurrence rollforward only ever operates on a tick's own claimed batch, never a fresh query
  — prevents a double-advance race between overlapping ticks.
- `byweekday` is 0=Sunday..6=Saturday on the wire (matches JS `Date.getDay()`), explicitly
  remapped to dateutil's 0=Monday convention server-side rather than via modular arithmetic.
- `until` is inclusive of that local calendar date in both the backend (`zoneinfo`-based) and
  frontend (day-granularity, UTC-instant-stepping) recurrence engines — the two are
  deliberately *not* required to agree to the minute, only to the day, since the frontend
  version is display-only and the backend is the actual source of truth for reminder firing.

### SSRF Guard (custom Daily Brew feeds only — not the curated catalog)
- Resolves the hostname via async DNS and rejects if **any** resolved IP is private,
  loopback, link-local, reserved, multicast, or unspecified (closes a DNS-rebinding gap a
  plain hostname blocklist would miss).
- Redirects followed manually, capped at 5 hops, re-validating scheme and re-running the
  private-IP check on **every** hop — closes the "public URL redirects to internal target" hole.
- (Frontend gap, flagged not fixed: `share/unfurl.ts`'s link-preview fetch has no equivalent
  guard on user-shared URLs.)

### GDPR Invariants
- Account deletion requires fresh password re-verification even for an already-authenticated
  session, and is unconditionally irreversible (no soft-delete/undo).
- Data export reads only from the local decrypted cache — the server never sees plaintext to
  export from in the first place once E2EE is fully live.
